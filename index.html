Roles & standard controls

How governance should work in the production system.

Recommended visit workflow

  1. Administrator creates teams and appoints each team's leader.
  2. Admin or member creates a visit and assigns it to a team and member.
  3. Assigned member records the visit outcome and marks it Completed.
  4. The completed visit enters the review queue and remains Pending review.
  5. Only the leader of that visit's team can approve or return it.
  6. Approval records reviewer, decision time and comments; return sends it back for correction.
  7. MIS and cross-team monitor can compare all teams; monitor access is read-only.

Technology recommendation

For a real multi-user web application hosted on Netlify, use Next.js or a static frontend plus Netlify Functions for server-side endpoints, a managed PostgreSQL database for shared records, and secure server-side role-based access control. Architecture

Netlify only, no separate server
  1. Two modes, chosen automatically: easy mode (no server functions: login in the browser, data in your cloud storage) or server mode (the Netlify function below).
  2. Browser loads one page, public/index.html (plain HTML, CSS and JavaScript; no framework, no build step).
  3. The page calls /api/* with JSON. One Netlify Function (netlify/functions/api.mjs) handles every request.
  4. The function checks the session cookie, the network and domain rules, the role permissions, and validates the input.
  5. Data is stored as 4 JSON documents in Netlify Blobs (store “visitops”). Saves use ETag compare-and-set, so simultaneous saves never overwrite each other.
  6. A scheduled function copies the data to Dropbox every night at 20:00 UTC (02:00 Bangladesh), keeping 30 days.
  7. Optional outgoing webhooks notify other services (signed with HMAC-SHA256).

Easy mode (Letter Desk style)

Default when no server functions exist
QuestionAnswer
Where is the data?In this browser (localStorage) and, if cloud storage is connected, in ONE file in your own cloud account: Appwrite, Google Drive (app data folder), OneDrive (app folder) or Dropbox (app folder). The file is encrypted (AES-GCM, key derived from the workspace password with PBKDF2, 150,000 rounds).
How does login work?Users are stored inside the data (salted PBKDF2 hashes). The first screen creates the administrator. People sign in with email or username. Sessions live in the browser (8 hours, or 30 days with Keep me signed in).
How do devices share data?Every device uses the same cloud settings and workspace password. Saves upload after 1.5 seconds; devices check for changes every 10-60 seconds (configurable) and on return to the tab.
What if two people save at once?Each upload carries a revision and a random write id. If the cloud copy changed, the device downloads it, re-applies its own unsynced actions on top, and uploads again. After each upload it re-reads the file to confirm nobody overwrote it.
What is different from server mode?No webhooks, no scheduled Dropbox backup (the cloud file is the copy; JSON backup download still works), no IP allow-list, no server-enforced permissions. Test mode and allowed email domains are settings inside the app (Admin Control).
How is the mode chosen?At start the page asks /api/policy. If the Netlify functions answer, server mode is used. If not (plain static hosting, drag-and-drop, file opened from disk) easy mode is used. cloud-config.js can force it with window.VO_FORCE_MODE.

  • Roles, visit visibility and approvals are enforced by the app running in each person's browser. Someone who knows the workspace password and is comfortable with browser developer tools can read or change any data. Use it for trusted teams.
  • The workspace password protects the cloud file. Anyone with the password can decrypt everything, including users and client names. Share it privately and change it by re-connecting every device if someone who knew it leaves.
  • Sign-in is a gate in the browser, not a server check (same model as Letter Desk).
  • With Appwrite the collection must allow 'Any' to create/read/update; the data is unreadable without the workspace password, but anyone could overwrite the file (denial of service). Keep the collection id private and keep backups (Admin Control -> download JSON backup).
  • Browser-only mode (no cloud) keeps data on one device only: clearing browser data deletes it. Download a JSON backup regularly.
  • IP allow-list and server-enforced permissions require server mode (Netlify functions).

Security controls

AreaControl
PasswordsSalted scrypt (N=16384, r=8, p=1); only the hash is stored. Policy: min length (default 6), obvious passwords refused.
SessionsSigned (HMAC-SHA256) cookie: HttpOnly, Secure, SameSite=Lax. 8 hours, or 30 days with "Keep me signed in". A per-user version (pv) ends sessions at once on role change, disable, reset or delete.
Brute force5 wrong passwords lock the account for 15 minutes. Setup code: 5 wrong tries pause setup 15 minutes.
CSRFEvery non-GET request needs header X-Requested-With: visitops and a same-origin Origin.
AuthorizationChecked on the server for every request (visibility and write scope per role). The browser only hides buttons.
Who may sign inALLOWED_EMAIL_DOMAINS and ALLOWED_IPS enforced on every request. IP comes from Netlify's x-nf-client-connection-ip header (not spoofable).
Browser protectionsnetlify.toml sets CSP (self only), HSTS, X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy.
WebhooksHTTPS and domain names only (no IPs/localhost/internal names), no redirects, 5 s timeout, HMAC-SHA256 signature header X-VisitOps-Signature.
ConcurrencyETag compare-and-set with retry: simultaneous saves never overwrite each other.
Test modeOPEN_ACCESS disables sign-in on purpose. /api/policy and the red banner make it obvious; npm run check reports it as a failure.

Operations

  • Deploy from Git or the Netlify CLI (not drag-and-drop). After deploying run: npm run check https://YOUR-SITE.
  • First administrator: set SETUP_CODE, create the account on the setup screen, then delete SETUP_CODE. Create a second administrator.
  • Joiners: create the user. Leavers: Disable (instant), later Delete. Forgotten password: Reset password.
  • Backups: nightly to Dropbox; manual backup and JSON download in Admin Control; test a restore every quarter.
  • Monitoring: /api/health and Netlify → Logs → Functions.
  • Rotate secrets: replace in Netlify and redeploy (SESSION_SECRET signs everyone out).
  • Staging: use a separate Netlify site. Deploy previews share the production data store.

Testing

  • npm run selftest: 62 automated checks (no Netlify account needed).
  • npm run check https://YOUR-SITE: post-deploy health check.
  • Manual acceptance script: docs/TESTING.md.
  • Team testing: switch on OPEN_ACCESS (test mode) to use the Test as menu and Load sample data; never with real data.

Known limits

  • Netlify Blobs suits small and medium teams (thousands of visits). The whole 'db' document is read and written on each change, so very large data or many simultaneous users need a database.
  • No email password reset by design: an administrator resets passwords.
  • Webhook delivery is attempted once (no retry).
  • The scheduled backup runs only on the published production deploy.
  • Single administrator-managed organisation (no multi-tenant separation).
  • Sessions are stateless cookies; revocation works through the per-user version number.

Only store.mjs touches storage. To move to a database (for example Postgres), re-implement read(name) and mutate(name, fn) with the same behaviour (fn edits the document and returns a value; throw to abort; retry on conflict). The API and the front end do not change.
